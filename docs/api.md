# API 参考

以下接口仅用于文档展示，不提供真实服务。本页演示如何用 Markdown 描述一份接口文档的结构：
接口说明、参数表格、请求示例、返回示例、错误码。

## 查询文档列表

返回站点中所有文档条目的列表，用于构建目录页或搜索索引。

- 请求方法：`GET`
- 请求路径：`/api/docs`
- 功能：返回文档条目列表。

### 请求参数

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | query | integer | 否 | 页码，从 1 开始，默认 1 |
| `size` | query | integer | 否 | 每页条数，默认 20，最大 100 |
| `keyword` | query | string | 否 | 按标题模糊匹配 |

### 请求示例

```bash
curl -X GET "https://xiangsi-max.github.io/my-docs/api/docs?page=1&size=20&keyword=指南"
```

### 返回示例

```json
{
  "items": [
    {"id": 1, "title": "使用指南"}
  ],
  "page": 1,
  "size": 20,
  "total": 4
}
```

## 查询单篇文档

- 请求方法：`GET`
- 请求路径：`/api/docs/{id}`
- 功能：按 ID 返回单篇文档的标题与正文。

### 路径参数

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `id` | integer | 文档唯一标识 |

### 返回示例

```json
{
  "id": 1,
  "title": "使用指南",
  "content": "本页说明一次完整的改文档到上线流程。",
  "updated_at": "2026-11-09T22:00:00+08:00"
}
```

## 错误码

| 状态码 | 含义 | 处理建议 |
| --- | --- | --- |
| `200` | 请求成功 | — |
| `400` | 参数格式错误 | 检查 `page`、`size` 是否为整数 |
| `404` | 文档不存在 | 确认 `id` 是否存在 |
| `429` | 请求过于频繁 | 降低频率后重试 |
| `500` | 服务内部错误 | 记录请求 ID 后联系维护者 |

## 字段约定

响应体统一使用 JSON，字段命名采用下划线风格，时间统一为带时区的 ISO 8601 格式：

```json
{
  "updated_at": "2026-11-09T22:00:00+08:00"
}
```

!!! warning "关于本页的说明"
    以上路径、参数与返回结构均为教学示例，站点本身是纯静态的，**没有后端服务**。
    写这一页的目的是练习「用表格描述参数、用代码块描述报文」的文档写法。

## 我写这一页的思路

我原本以为「API 文档」就是要写清楚每个接口干什么，动笔后才发现真正难的是**把不确定性写明白**：
参数是可选的还是必填的、默认值是多少、超出范围会怎样、出错了前端该重试还是该提示用户。
所以这一页我刻意按「参数表 → 请求示例 → 返回示例 → 错误码表」的顺序排，
让读的人从上往下看一遍就能拼出一个能跑通的请求，而不是先读三段说明再回去找参数。

写的过程中也确认了一件事：**错误码必须给出处理建议，不能只列含义。**
我最初只写了 `429 请求过于频繁`，后来发现光看这句话，调用方并不知道该立刻重试还是该退避，
补上「降低频率后重试」之后这一行才有实际作用。文档的价值不在于描述现状，
而在于让读的人在遇到问题时知道下一步做什么。

另外，这一页本身是纯静态站点的一部分，没有真实后端，所以我在末尾加了一条 `warning` 说明，
避免有人真的去请求这些路径。**教学示例要显式标注自己是示例**，否则读者会误以为能用。
